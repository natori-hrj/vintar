# Vintar v0.7.0 Pure Go 互換性契約

契約の版は 1。実装基点は `f36fed7ca74ed5e89a67fcce3c86e6b2fcf21779`、文書の編集基点は `f15e9902bdb639034007a6f2b6ca5c271fd8790b`。公開挙動の参照はリリースタグ `v0.6.0` のコミット `712e507f04684d0cc9ba1f62bec6448b274ac87c`。以下のファイルパスは同タグで解決する。明記した版表示・配布対象・安全上の例外を除き、リリースの公開挙動を優先する。

配布対象は Go バイナリ。Python ランタイム、SDK、バインディング、二重エンジンを採用しない。参照用 Python は、既存の履歴と証拠から移行時に期待結果を採取するために使える。認可内部実装 #93–#95、保存候補 #96–#97 など、v0.6.0 に含まれない機能は後続に送る。

## Go と配布

- Go 言語の最低版は `1.26.0`（`go.mod` の `go` 行）。製品は `CGO_ENABLED=0` でビルドし、実行に CGO や Python を必要としない。対象の `GOOS/GOARCH` は `linux/amd64`、`linux/arm64`、`darwin/amd64`、`darwin/arm64`、`windows/amd64`。
- ツールチェーンが対象を認識すること、小さなプログラムをクロスビルドできること、または製品バイナリがクロスビルドできることは、製品が対象環境で動作する証拠ではない。ツールチェーン確認・製品ビルドと、対象環境で製品バイナリを起動して得た CLI・ファイル・中断の適合結果を別に記録する。対応環境での race 検査は別枠であり、CGO 有効の検査結果は CGO 無効の製品検査を代替しない。

## CLI

比較対象はコマンド階層、公開オプション・別名、使い方と診断の意味、出力先、終了値、成果物。help の色、罫線、列配置、折り返しなどの装飾をバイト一致させる必要はない。JSON とダイジェストの契約はこの除外に含めない。

| 入口 | v0.6.0 の契約 |
| --- | --- |
| `version` | stdout に `Vintar v0.6.0\n`、終了 0。移行版の表示は `Vintar v0.7.0\n`。 |
| `--help`、サブコマンドの `--help` | 対象の公開コマンド、位置引数、必須・任意オプションを stdout に表示し終了 0。引数なしのルートと `sqli` は stdout に help、`http` は stderr にサブコマンド不足の診断を出し、いずれも終了 2。未知のコマンド、未知のオプション、必須不足、余分な位置引数などのパースエラーは stderr に診断を出し終了 2。 |
| `--show-completion`、`--install-completion` | ルートの補完オプションを保持する。前者は検出されたシェル用の補完スクリプトを stdout に出す。後者はユーザー環境に補完を登録し、stdout に結果を出す。正常時は終了 0。Go 版のスクリプトは生成方式やバイト列を固定せず、補完候補と導入の意味を比較する。導入は隔離したホームで検証する。 |
| `verify` | 必須の `--cases` は単一の通常 TOML ファイル、または非再帰のディレクトリ。直下の `.toml` をファイル名順に実行し、空または 128 件超、シンボリックリンクの入力パス、通常ファイルでない `.toml` エントリを拒否する。`--authorized`、`--pretty`。上限系は下表。環境設定と通信条件は実行安全性を参照。 |
| `http send` | 位置引数は `METHOD URL`。`--body`、反復可能な `--header/-H`、`--cookie/-C`、`--param/-p`、`--timeout/-t`（既定 10 秒、0.1–60 秒）。メソッドは大文字化して GET / POST のみ受理。パース後の未対応メソッド、不正な分割形式、送信エラーは stdout の診断と終了 1（パースエラーの 2 とは別）。レスポンスを受け取れば HTTP ステータスにかかわらず終了 0。stdout は `Target`、`Method`、`Status`、`Response time`（秒、小数 3 桁）、`Content size`（bytes）の順で、本文ではない。サイズは読み取った本文の上限 1 MiB までの値。429 では本文を読まず 0 bytes。 |

| `inventory-post-json` | 必須の `--spec --output`。ローカル OpenAPI から inventory ファイルを出力。stdout は `POST JSON inventory:` に続く operations、case-generatable、fields、injectable、diagnostics の件数を示すテキスト。 |

公開パーサーの構文は独自に狭めたり広げたりしない。`--option value` と `--option=value`、短い別名、`--`、スカラー指定の重複時の優先順、反復指定の順序をリリースと比較する。`http send` では `--timeout` と `-t` が混在しても最後の指定を範囲検査する。ヘッダーは最初の `:` で分割し名前と値の両端を除去、cookie は最初の `=` で分割し名前だけの両端を除去する。同じ名前の値は後の指定を使う。`--param` は最初の `=` で分割して空の名前を拒否し、値の空文字を許し、重複名も指定順のまま保持する。`http send` で `--param` を指定すると URL の既存クエリを置換する。

| `verify` のオプション | 既定値 | 範囲（両端を含む） |
| --- | ---: | --- |
| `--max-requests` | 48 | 1–768 |
| `--rps` | 2.0 | 0.1–10.0 |
| `--timeout` | 10.0 | 0.1–60.0 秒 |
| `--time-deadline` | 45.0 | 0.1–120.0 秒 |
| `--max-response-size` | 1048576 | 1–1048576 バイト |

`verify` は完全 PASS で 0、FAIL で 1、FAIL 以外の不完全または INCONCLUSIVE で 3。期待と一致する INCONCLUSIVE も合格扱いから外れる。0/1/3 では stdout に末尾改行付きの batch report v1 を 1 件出し、stderr に診断を分離する。入力・設定・有効な結果を生成できない実行エラー・出力エラーは 2、中断は 130。出力前の拒否・中断では stdout は空。書き出し中の失敗では部分出力が残り得る。`verify` と `sqli verify` の `--pretty` はインデントを変え、JSON の意味を変えない。オフラインコマンドは成功時に上表の完了情報と成果物を出し終了 0。入力・成果物出力の失敗は stderr と終了 2、中断は終了 130（いずれも処理中に捕捉される場合）。

**受け入れ**。タグの `tests/test_cli_goldens.py` と `tests/golden/cli/` をシナリオ単位で対応づける。Go のバイナリをサブプロセス起動し、終了値、stdout の空／テキスト／単一 JSON、stderr の診断、生成ファイルを別々に比較する。JSON はキーの有無、型、`null` と省略の差、配列順を保持し、期待結果の正規化は fixture ごとに記録する。コマンド固有の根拠は `src/vintar/cli.py`、`src/vintar/*_cli.py`、`src/vintar/core/http.py`、`tests/test_{cli_version,http_cli,sqli_cli,regression_cli,discover_cli}.py`。リリース実バイナリ相当のプロセスで、引数なしのルート・各グループの出力先、フレームワーク由来の補完オプション、短い別名の結合や重複の扱い、ハンドラ外の中断を追加照合する。明示 help、未知オプション、必須不足、範囲境界と直外、競合、中断をそれぞれ独立に扱う。

## データ契約

- TOML は Case Schema v1 と v2 の既存入力を受理する。v2 の同梱スキーマとルート `schemas/regression-case-v2.schema.json` の一致を検証する。欠落・未知フィールド、型違い、重複、条件付き必須、明示空文字と省略の差をタグのローダーで照合する。
- JSON レポートは `schemas/` の公開スキーマを基準にする。batch v1 は `schemas/regression-batch-report-v1.schema.json` と過去の fixture でも検証し、JSON 内の `exit_code` はプロセス終了値と一致させる。POST JSON inventory と POST review の成果物は v2 を書き出し、v1/v2 の既存 reader の受理範囲は writer と分けて固定する。stdout の完了情報は成果物そのものではない（例: POST review の完了 JSON は v1、POST ケース生成の完了 JSON は v2）。draft、review、materialization、単一チェックの出力は CLI golden と実装を照合する。
- OpenAPI 3.0/3.1 のローカル JSON/YAML を扱う。YAML は単一文書で、アンカー、エイリアス、明示タグ、プレーンなマージキー、文字列以外のキー、重複キーを拒否する。プレーンな `null`、`true`、`false` と JSON 数値構文だけを型変換し、日付や `yes` などは文字列として扱う。参照の許容範囲、循環、入力と展開の上限は `src/vintar/regression/discovery.py` と fixture に従う。外部参照を取得しない。
- strict JSON は 1 MiB、ルート深さ 0 から深さ 48、整数 4300 桁（符号を除く）。厳密な UTF-8、単一値、重複キー拒否、整数精度、有限の binary64 浮動小数点を守る。サイズなどの上限は各入力経路の実装も照合する。
- 承認連鎖に使うダイジェスト・ID の入力バイト列は呼び出し元ごとに v0.6.0 と照合する。strict canonical JSON と本文の canonical JSON はキー順、空白なし、ASCII エスケープ、整数と浮動小数点の区別、配列順、負のゼロ、指数表記を保持する。strict JSON 本体はエスケープ済み孤立サロゲートを受理して再エスケープする。OpenAPI 入力には別の Unicode 検証がある。baseline の SHA-256 には `core/json_body.py` の bytes を使う。`discovery.py` の入力 ID には既定の区切り空白を含む別の表現があるため、全 ID を一つの JSON writer に統一しない。JSON Pointer のエスケープと配列添字の境界も保持する。
- ファイル出力はコマンドによって異なる。`discover --output` と `inventory-post-json` の inventory writer は入力と同一の出力（リンクによる別名を含む）を拒否するが、独立した既存レポートは一時ファイルから置き換えられる。ドラフト・レビュー・ケースの writer は既存の同一内容を再利用し、内容の異なる既存ファイルを上書きしない。ケース生成は現在の入力から再計算したレビューと照合する。入力との同一ファイル判定、失敗時の残存ファイル、ハードリンク利用条件を別々に観測する（`src/vintar/{discover,post_json_inventory}_cli.py`、`src/vintar/regression/{discovery_drafts,discovery_review,post_json_review,case_materialization}.py`）。

**受け入れ**。タグのケース TOML と JSON fixture、`test_identity_binding_contracts.py`、`test_post_json_{inventory,review}_validation.py`、過去の batch v1 fixture を使う。追加する小さなベクトルは canonical bytes と SHA-256 の両方、受理・拒否の境界、未知フィールド、既存 artifact の再検証を対象にする。通常の Go 直列化で差が出るものを先に赤にする。

| `{"é":1.0,"b":"<"}` | `{"b":"<","\u00e9":1.0}` | `4059700a09ba87c8cccbabfe931027238356fb0c43fc8e444a973783dcdd8d87` |
| `{"\ud800":-0.0,"v":1e-7}` | `{"v":1e-07,"\ud800":-0.0}` | `50852f2f2cea7a2c37c452f0e5caafa1088c801b56292c8ce3a2779393ccc8d6` |

## 実行安全性

- `verify` は実行前に明示の `--authorized` と信頼済み環境設定を要求する。v1 は `VINTAR_TARGET_ORIGIN` と `VINTAR_ALLOWED_ORIGIN`。v2 は `VINTAR_TARGET_ORIGIN` と operator が管理する `VINTAR_RUNTIME_POLICY_JSON` または `VINTAR_RUNTIME_POLICY_FILE` を使う。inline が設定されていれば空文字も含めて優先し、無効でも file にフォールバックしない。v2 の各実行上限は CLI 値とポリシー値の小さい方。v1 と v2 の混在バッチは終了 2 で拒否する。ケース情報のみで通信権限は生じない。
- v2 は承認をケース ID、実行 identity、メソッド、パス、origin、環境区分に束縛する。POST はさらに operation と baseline のダイジェスト、隔離環境、レビュー済み `no_side_effect` を要求する。認証情報は承認済み送信時だけ適用し、ケース、レポート、診断に流出させない。
- `sqli verify` は明示の `--authorized` と `--allow-origin` を使う。`http send` は別の汎用検査コマンドで、`verify` のケース・信頼済みポリシーを受理しない。検査コマンドごとのリクエスト予算、レート、タイムアウト、Time のケース単位の期限、レスポンスサイズを該当経路で強制する。リダイレクト、自動リトライ、POST リプレイは禁止。中断後に新規通信を行わない。origin の照合は DNS 解決後の IP を検査するものではない。信頼境界には実行環境の通信制限も必要。
- `VINTAR_RUNTIME_POLICY_FILE` などタグで `read_bounded_regular_file` を使う入力は、末尾リンクを追跡せずに開いた同じハンドルから、通常ファイルだけを上限付きで読む。Windows での対応は同等の安全性を満たす場合に限る。安全な読み取りを保証できない環境では拒否し、リンク追跡ありの読み取りに切り替えない。
- オフラインコマンドは通信件数 0。`verify` はバッチ全体を送信前に事前検証し、承認欠落・不一致では送信件数 0 とする。公開レポートは既存の許可フィールドだけを出し、判定ラベルの意味を変えない。
- **安全が出力互換に優先する。** 旧 CLI の診断が入力断片や下位の例外を表示する場合（例: `http send`）でも、秘密値や機密パスを再出力しない。通常の診断の種類、出力先、終了値は保ち、必要な値だけを伏せる。通常の `Target` 表示でも認証情報を再出力しない。安全な入力・成果物の分離、非上書きが必要な writer の保護、通信の承認・上限・キャンセルを保証できない場合は成功を装わず拒否する。

**受け入れ**。既存の `test_post_json_policy.py` と公開入口の拒否 golden でゲートを固定する。将来の Go テストでは外部通信を切った環境で、承認失敗時の transport 呼び出し数 0 とシークレットの非出力を検証する。承認済みのローカル無害フィクスチャでのみ許可経路を検証し、転送先への通信数 0、上限到達後の追加通信数 0、キャンセルを観測する。時計は制御可能にし、バイナリを使う少数のテストで配線を確認する。
