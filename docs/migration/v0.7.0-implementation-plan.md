# Vintar v0.7.0 実装計画

[互換性契約](v0.7.0-compatibility.md) 版 1。今回の候補は互換性契約と実装計画の文書のみ。Go のコード、`go.mod`、CI、テスト、配布入口の変更は含まない。移行ブランチで将来の Go 実装と受け入れテストを揃え、製品ゲートを通過してから配布入口を切り替える。振る舞いの参照は `v0.6.0` に固定する。配布は単一 Go エンジンのバイナリとし、Python ランタイム、SDK、バインディング、二重エンジンは採用しない。旧 Python 実装は履歴と既存作業ツリーに保全し、期待結果の採取にのみ使う。

## 保全調査時点の記録

- 調査時点の main は v0.6.0 から 3 コミット進み、内部認可契約・合成・GET runner を含む。保存ブランチは `probe-catalog`（`d11adab`）と `discovery-skeleton`（`dbcf3db`）。元リポジトリでは双方の作業ツリーに変更なし。
- 元リポジトリの `.vintar-review-results/` に #96–#97 の候補パッチ、検証結果、再レビューがある。未追跡の `AGENTS.md` と `tools/pr-review/` も元の作業ツリーにある。Go 側の適合証拠は独立して採取する。
- 前回の [Pure Go 設計と保全調査](codex://threads/01a21ca3-7e9b-7b40-a891-cee22dc7b0ef) を確認した。単一モジュール、実行配下に閉じた HTTP 送信、オフライン検証先行を引き継ぐ。旧調査が記録した一時マニフェストは現環境では参照できず、現在の Git 状態と残存レビュー証拠を直接確認した。`docs/design/enterprise-api-security.md` は Python 側の設計資料として扱う。承認済みの方向と v0.6.0 の実装を今回の判断に使う。
- 元リポジトリに 407 GiB、作業環境の /tmp に 4.5 GiB の空きがあり、保全対象の削除は不要だった。元の Git メタデータは読み取り専用のため独立クローンに移行ブランチを作成した。書き込み範囲の排他を強制できる writer セッションを確立できないため直列で取りまとめた。

## パッケージ境界

コマンド中心の一体構成は初期の配線が単純だが、オフライン処理の送信不能性と transport の呼び出し境界を検査しにくい。Python のディレクトリ構成を機械的に移植すると歴史的な層と相互依存を持ち込む。単一 Go モジュールの `internal` を使い、パッケージの依存方向を固定する。複数モジュールに分けるとバージョン管理と配布を同期させる負担が増える。

| パッケージ | 責務 |
| --- | --- |
| `cmd/vintar`、`internal/cli` | 引数、環境の取り込み、入出力と終了コード。 |
| `internal/casefile`、`internal/strictjson`、`internal/report` | バージョン別のケース、厳密な JSON、レポート。入口や通信に依存しない。 |
| `internal/discovery`、`internal/review` | OpenAPI とオフライン生成。実行と transport への依存を持たない。 |
| `internal/execution`、`internal/execution/internal/httpio` | バッチ事前検証、信頼済みポリシー、予算、調停、認証適用と HTTP 送信。下位の HTTP 実装への直接依存を Go の可視性で実行パッケージ配下に限定する。 |
| `internal/decision` | 型付き観測値から既存ルールで判定を返す純粋処理。 |

型と関数は利用者を持つ時点で確定する。Go 依存の導入では CGO 無効ビルド、ライセンス、厳密なパース、名前付き型の境界を確認する。

## Go と配布対象

- 最低サポート版は **Go 1.26.0**。実装時の `go.mod` に `go 1.26.0` を明記する。この最低版を CI に正確にインストールし、`GOTOOLCHAIN=local` で自動切替・更新なしに検証する。リリースにはリリース時点でサポート対象の最新セキュリティ修正版を使い、実際に使ったパッチ版を記録する。新版での成功は最低版ゲートの代わりにならない。
- 製品ゲートと配布ビルドでは `CGO_ENABLED=0` を必須とする。`-race` は race detector が CGO を要するためこの条件では適用しない。対応する Go/OS/arch と C ツールチェーンが揃う場合のみ、`CGO_ENABLED=1 go test -race ./...` を別の計測ジョブとして実施できる。計測結果で製品ゲートを代替せず、その成果物も配布しない。
- 配布対象は `linux/amd64`、`linux/arm64`、`darwin/amd64`、`darwin/arm64`、`windows/amd64`。各ターゲットのバイナリを対応する OS/arch 上で実行して適合を確認する。クロスビルド成功だけではランタイム適合としない。

## 順序と排他所有

| 順序 | 所有範囲 | 依存・昇格条件 |
| --- | --- | --- |
| 0 | 契約レビュー（今回の文書候補） | `v0.6.0` の実装・テストと照合し、公開互換性と安全性の差分判断、受け入れ条件を承認・記録する。契約レビューの承認なしにエンジン実装へ着手しない。 |
| 1 | CLI 担当が `cmd/vintar`、`internal/cli`、CLI golden を所有 | バージョン、help の意味、無効引数の subprocess チェックを固定。次に JSON 出力と終了コードを対応づける。 |
| 1 | データ担当が `internal/{casefile,strictjson,report,discovery,review}` とデータ fixture を所有 | タグ由来の正負ベクトルが必要。CLI 担当とは型とエラー分類のみ合意する。 |
| 1 | 安全性担当が安全性の受け入れ仕様・拒否シナリオを所有 | 契約に基づき、送信 0 回を先に検証する設計を確定する。 |
| 2 | 統合担当が `go.mod`、CI、テスト共通入口を所有 | オフラインコマンドを CLI に結合し、既存 JSON・生成ファイルを比較する。 |
| 3 | 別工程で `internal/{execution,decision}` を実装 | 工程 0 の承認が必須。拒否、上限、中断、秘密非出力の受け入れが通ってから許可経路を結合する。 |
| 4 | 配布・運用担当 | Go バイナリで CI テンプレートと成果物検証を通す。公開対象の OS/arch で配布物をリハーサルする。 |

Go の実装開始時は既存 fixture で表せる公開挙動を先に実行する。差が出る境界は小さなテストを先に失敗させ、修正後に対象と全体を確認する。

## CLI 互換性と実装時の確認事項

- 公開 CLI の意味を保持する。コマンド、引数、フラグと短縮形、既定値と範囲、重複・順序の意味、終了コード、stdout/stderr の役割、機械可読出力と成果物を参照と照合する。help は公開入口・引数・オプションと終了コード・出力先を確認し、バイト完全一致は要求しない。Typer の装飾、折り返し、レイアウトは固定しない。暗黙の補完オプションや非 TTY 表示は観測し、公開挙動への影響がある差は契約レビューで扱う。
- JSON の孤立サロゲート、境界浮動小数点、YAML 暗黙型、TOML 数値と日時はリリース実装で期待値を測り、ライブラリの既定値だけに依存しない。出力のうちハッシュに入る bytes とそれ以外の整形要件を fixture で明示する。
- Go のモジュールパスはリポジトリの公開 URL に合わせて `github.com/natori-hrj/vintar` とする。ファイル操作の安全性と中断は配布対象ごとに下記のランタイムゲートで検証する。
- v0.6.0 の測定対象に入らない振る舞いや、安全性との衝突が判明した場合は、呼び出し元に見える差と証拠を明記して契約判断に戻す。

## 検証計画（実装工程の製品ゲート）

参照タグのチェックアウトで次を実行する。参照用 Python の検証結果は Go 適合結果とは分けて記録する。

```sh
uv run --locked pytest -q tests/test_cli_goldens.py tests/test_cli_version.py \
  tests/test_post_json_inventory_validation.py tests/test_post_json_review_validation.py \
  tests/test_identity_binding_contracts.py tests/test_post_json_policy.py
```

Go 1.26.0 と `CGO_ENABLED=0` で標準ライブラリのみの確認用プログラムを全 5 対象にビルドし、バイナリのビルド情報を照合した。ネイティブ実行は `linux/amd64` で確認した。以下の製品ゲートは Go コードとテスト入口が揃った後に実行する。

### 最低版とリリース版のソースゲート

クリーンなチェックアウトで、公式の `go1.26.0` 配布物を公開 SHA-256 と照合して導入し、`GO_ROOT` にその展開先の Go ルートを指定する。最低版では `EXPECTED_GO_VERSION=go1.26.0`。依存方向の検査は `go test ./...` に含め、`go list -deps` 等の結果でパッケージ境界を検証する。

```bash
set -euo pipefail
export PATH="${GO_ROOT:?}/bin:$PATH"
export GOTOOLCHAIN=local CGO_ENABLED=0
test "$(go env GOVERSION)" = "${EXPECTED_GO_VERSION:?}"
test "$(go env CGO_ENABLED)" = 0
grep -Fxq 'go 1.26.0' go.mod
unformatted=$(git ls-files -z -- '*.go' | xargs -0 gofmt -l)
test -z "$unformatted" || { printf '%s\n' "$unformatted"; exit 1; }
go mod verify
go test -count=1 ./...
go vet ./...
```

リリース用の固定パッチ版でも `GO_ROOT` と `EXPECTED_GO_VERSION` を切り替えて同じゲートを実行し、さらに CI で版を固定した `govulncheck ./...` を実行する。`go.mod` の最小版と `GOTOOLCHAIN=local`、`CGO_ENABLED=0` は共通とする。

### 配布ビルドとターゲット別ランタイムゲート

最低版とリリース用の固定パッチ版の両方で、対応する `GO_ROOT`、`EXPECTED_GO_VERSION` と別々の `OUT_DIR` を指定して 5 対象をビルドする。リリース用ツールチェーンの成果物をネイティブ実行ゲートに渡す。

```bash
set -euo pipefail
export PATH="${GO_ROOT:?}/bin:$PATH"
export GOTOOLCHAIN=local CGO_ENABLED=0
test "$(go env GOVERSION)" = "${EXPECTED_GO_VERSION:?}"
for target in linux/amd64 linux/arm64 darwin/amd64 darwin/arm64 windows/amd64; do
  os=${target%/*}
  arch=${target#*/}
  exe=vintar
  if [ "$os" = windows ]; then exe=vintar.exe; fi
  dir="${OUT_DIR:?}/$os-$arch"
  mkdir -p "$dir"
  GOOS="$os" GOARCH="$arch" go build -trimpath -o "$dir/$exe" ./cmd/vintar
  go version -m "$dir/$exe"
  (cd "$dir" && sha256sum "$exe" > "$exe.sha256")
done
```

各ネイティブ CI ジョブではその成果物を取得し、ビルド時に記録した SHA-256 と照合する。固定したリリース用ツールチェーンを使い、`GOTOOLCHAIN=local go env GOVERSION GOOS GOARCH` が固定版および対象ペアに一致することと、ランナー自体も対象ペアであることを確認する。下記のテスト入口と環境変数名は実装時に用意する予定で、`VINTAR_TEST_BINARY` は配布候補の絶対パスとする。POSIX と Windows PowerShell の起動例：

```sh
GOTOOLCHAIN=local CGO_ENABLED=0 VINTAR_TEST_BINARY="$ARTIFACT" \
  go test -count=1 -v ./internal/acceptance -run '^TestProductBinary$'
```

```powershell
$env:GOTOOLCHAIN = 'local'
$env:CGO_ENABLED = '0'
$env:VINTAR_TEST_BINARY = $ARTIFACT
go test -count=1 -v ./internal/acceptance -run '^TestProductBinary$'
if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
```

テストはバイナリをサブプロセスで起動し、CLI の公開挙動とオフライン成果物に加え、5 ペアそれぞれで次を確認する。必須シナリオの未実行や skip は合格とせず、ターゲット、Go 版、成果物、シナリオ別結果を記録する。

- **ファイル競合**：互換性契約に従い、レポートの置換と、下書き・レビュー・ケースの上書きなしの公開を別々に検証する。入力と同一ファイルを指す出力や、適用対象のシンボリックリンクを拒否し、Windows では対象の再解析ポイントも検査する。失敗時の既存ファイルと一時ファイルも確認する。
- **ハードリンク**：同一内容の再利用、異なる既存出力の保持、ハードリンクで同じ入力を指す出力の拒否を検証する。必要な排他的公開をファイルシステムが提供しない場合は安全にエラーとし、部分書き込みや上書きに切り替えない。
- **中断**：処理開始を確認してから Linux/macOS では SIGINT、Windows ではコンソールの Ctrl+C を発生させる。終了コード 130 が規定時間内に返り、中断後の新規送信と未完成の公開ファイルが 0 件であることを確認する。中断前に公開済みの完全なファイルは残りうる。

切替条件は未承認の公開差分 0 件、承認拒否・オフライン経路の送信 0 件、予期しない転送・再送・中断後の追加送信 0 件、機密の流出 0 件。通信安全性は外部通信を切った環境で、ローカルの無害フィクスチャと制御可能な transport で確認する。
