# Vintar v0.7.0 Go distribution preparation

**Status: rehearsal only.** No Go release or module tag has been published.
The existing PyPI `vintar==0.6.0` release and Python source remain available.
This candidate is not a full drop-in replacement for v0.6.0.

## Install and verify

For a checked-out candidate, use Go 1.26.0 or newer and confirm the checkout
SHA against the candidate you intend to test:

```sh
git rev-parse HEAD
CGO_ENABLED=0 go install -trimpath -buildvcs=true ./cmd/vintar
vintar version
go version -m "$(command -v vintar)"
```

Put `GOBIN` (or the `bin` directory under `go env GOPATH`) on `PATH`. The
candidate reports `Vintar v0.7.0`. Check the command path, Go version, target,
`CGO_ENABLED=0`, `vcs.revision` and `vcs.modified=false` in build metadata.
Runtime Python is not required.

After an authorized `v0.7.0` tag is available through the Go module ecosystem,
the intended remote install is:

```sh
CGO_ENABLED=0 go install github.com/natori-hrj/vintar/cmd/vintar@v0.7.0
```

The rehearsal verifies this versioned install using an isolated **local file
proxy** seeded from the exact commit; it does not create a tag or verify public
proxy availability. The version-qualified install records the module version in
`go version -m`; its binary need not match the stamped checkout-built archive
binary. It uses your selected Go toolchain, rather than the release archive's
pinned toolchain.

## Package layout and target status

| Target | Prepared archive | Native acceptance |
| --- | --- | --- |
| Linux/amd64 | `vintar_v0.7.0_linux_amd64.tar.gz` | Product CLI checks executed; the full R1 gate is separate |
| Linux/arm64 | `vintar_v0.7.0_linux_arm64.tar.gz` | Cross-build only |
| macOS/amd64 | `vintar_v0.7.0_darwin_amd64.tar.gz` | Cross-build only |
| macOS/arm64 | `vintar_v0.7.0_darwin_arm64.tar.gz` | Cross-build only |
| Windows/amd64 | `vintar_v0.7.0_windows_amd64.zip` | Cross-build only |

The archive contains `vintar` (`vintar.exe` on Windows), this guide as
`README.md`, the project `LICENSE`, and the toolchain and linked module
licenses/notices under `licenses/`. A separate CycloneDX 1.6 `*.cdx.json` for
each target inventories the linked Go modules and Go standard library; it does
not include test-only tooling. `provenance.json` records the source SHA, pinned
archive, build recipe, independent-build checksums, and archive/SBOM digests in
an **unsigned** in-toto Statement. It is neither a signed attestation nor a
claim of a SLSA level.

Obtain `SHA256SUMS` through a trusted source before verifying any future
download. With the archives and metadata together, run `sha256sum -c
SHA256SUMS` (or `shasum -a 256 -c SHA256SUMS` on macOS). For a single archive
on Windows, compare `Get-FileHash -Algorithm SHA256 .\vintar_v0.7.0_windows_amd64.zip`
to its line in the manifest. Extract only after verification, put the binary
on `PATH`, and run `vintar version`. The manifest verifies integrity relative
to trusted values; it is not a signature.

## Offline rehearsal and publication boundary

On Linux/amd64, preseed the `go1.27.4.linux-amd64.tar.gz` official archive and
the candidate's module download cache in a separate preparation step. Use a
clean full checkout with no ignored or untracked outputs. Supply a new output
directory outside the checkout; its parent must already exist. In a namespace
with no external network access but loopback enabled for the Go test fixtures:

```sh
export GOMODCACHE=/absolute/path/to/preseeded/modules
bash scripts/rehearse_go_release.sh <candidate-sha> /path/to/go1.27.4.linux-amd64.tar.gz /path/to/new-output
```

The rehearsal checks the archive SHA-256, dependency cache, clean candidate
SHA and native version, reuses the Go foundation gate's two independent builds
per target, and repackages twice with fixed archive metadata. `dist/` contains
the archives, manifest, SBOMs and provenance; `evidence/` records build
metadata, target comparisons and the offline `go install` check.

`Vintar Go release rehearsal` is a branch-only manual GitHub Actions workflow
that requires the exact selected SHA. It seeds pinned inputs, then runs the
rehearsal without external networking. It has read-only repository access and
prints checksums into the job summary. Outputs otherwise stay on the runner:
there is no artifact upload, tag creation, GitHub Release, or PyPI step. The
historical Python release workflow is separate and unchanged. Its version-tag
trigger must be considered separately before a future Go distribution cutover.
No hosted rehearsal is claimed by local results.

## Migration and release blockers

- Keep using the historical v0.6.0 Python CLI for its published behavior.
  Pin `vintar==0.6.0` when installing from PyPI and check which binary your
  shell resolves if you also build the Go candidate.
- The Go candidate has version/help, completions, `http send`, and the
  offline `discover`, `review-draft`, `inventory-post-json` and
  `review-post-json` entry points. Public `verify`, `sqli verify`,
  `materialize-case` and `materialize-post-json-case` are unavailable.
  C5/C7 compatibility work is still suspended; existing v0.6.0 artifacts are
  not guaranteed to be accepted by the Go candidate.
- The approved [compatibility exceptions](https://github.com/natori-hrj/vintar/blob/60cec83efb18e4fd85dc874180d0175a2bbc8f86/docs/migration/v0.7.0-release-blockers.md#承認済みの互換性例外)
  include stricter rejection of concealed symlink traversal and bounded
  command-wide POST operation-definition digest work. These do not change
  the separately bounded C7 baseline body or imply full compatibility.
- R2 hosted build verification passed for the preserved baseline in
  [run 46136461451](https://github.com/natori-hrj/vintar/actions/runs/46136461451).
  R1 and outstanding public compatibility are prerequisites to releasing.
  R3 preparation does not authorize publication or the distribution cutover.
